# Load-test reports

One folder per run: `report.md` (read this), `report.json` (everything), and raw `*.ndjson` events (not committed). `ledger.json` records the estimated QStash spend of every charged step against the $25 cap.

| Run | Target | What it shows |
|---|---|---|
| [dryrun-standin-3classes](dryrun-standin-3classes/report.md) | The local **stand-in** (not the app): in-memory queue, not QStash; Postgres and Electric in Docker on a laptop | The harness end to end at 90 students, 20× the testing-day rate. Its failures describe the stand-in and the laptop, not the app. |
| [local-app-3classes](local-app-3classes/report.md) | The **real app** (production build, `NODE_ENV=production`) on a laptop, Postgres and Electric in Docker. Its queue is the app's inline in-process queue, since QStash runs only in a Vercel production deploy. The inline mock grades by student name, not by whiteboard, hence "grades in a state the fixture does not predict". | 90 students at 20× the testing-day rate: 0 lost, dashboard p95 5.9 s, submit p99 1.38 s (fails the 1 s bar). |
| [qstash-smoke-local](qstash-smoke-local/report.md) | The real app's production build (one Node process) on a laptop, grading through **QStash's local dev server** (parallelism 100) and the real consumer, mock model `seed` profile | 30 students at 20× rate: 0 lost, 0 fixture mismatches, dashboard p95 9.8 s, submit p99 2.0 s (FAIL). |
| [smoke-production](smoke-production/report.md) | **Vercel production**: Functions, Blob, cloud QStash (free plan, parallelism 10), self-hosted Electric; mock model `seed` profile | One class of 30 at 10× rate: **PASS** on every criterion. Submit p99 0.66 s, dashboard p95 9.2 s, 0 lost, 0 failures, 0 fixture mismatches. In-flight grades peaked at 10, the QStash free plan's parallelism. |
| [ramp-local-qstash](ramp-local-qstash/report.md) | The real app's production build as **one Node process** on a laptop, QStash's local dev server (parallelism 100), Postgres and Electric in Docker; working window × 0.25, bell at real time | 990 students (peak 57 submits/s): FAIL. Lost 0, failures 0%, but submit p99 49 s and dashboard p95 254 s. The single process saturates: joins time out, the consumer and the shape proxy share it, queue wait p95 86 s, sync lag 114 s median. The generator peaked at 80% CPU (a 949 ms event-loop spike), so latencies are somewhat inflated. Vercel runs many instances; this is a per-process ceiling, not the deployed one. |
| [ramp-local-6workers](ramp-local-6workers/report.md) | The same build as **6 Node worker processes** on one port (`scripts/cluster.mjs`), a rough stand-in for several Vercel instances, sharing the 8-core laptop with the generator, Postgres and Electric | 990 students (peak 22 submits/s): FAIL. Lost 0, failures 0%, queue wait p95 1.3 s, grading p95 9.3 s. Submit p99 5.8 s (cause not isolated: the report labeled it "Database", but only 4 of 42 connections ever waited on a lock, so that label overstated it; the laptop's CPU was shared by everything) and dashboard p95 49 s, almost all of it sync: outcome to dashboard p95 44 s, with 414 shape-proxy 500s. **Electric is the first component to fail.** Each student's grades are a separate shape (`student_id = $1`), so 990 students mean about 1,000 shapes for Electric to match every write against. Generator healthy: 69% CPU, 196 ms event-loop p99. |
| [provider-down-local](provider-down-local/report.md) | The app as 6 local processes, QStash local dev server, mock `seed` profile with the provider down for 5 minutes (from 90 s into the step) | 300 students: **0 failed grades and 0 lost** through the outage, which is the outage bar. The queue held up to 585 grades and drained after the provider came back; submit p99 0.62 s. Dashboard p95 192 s misses the 30 s bar because the outage itself delays grades by up to 5 minutes: delayed, not failed, as designed. |
